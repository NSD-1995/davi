# DAVI implementation audit — 30 October 2026

## Verdict and scope

DAVI is a substantial school operations MVP, but it is not finished or ready for an unrestricted production launch. Academic administration and daily operations have broad implementations; public registration, credential exposure, authorization consistency, release verification, mobile, and external communication need work.

This audit inspected repository structure, current source, Prisma models/migrations, route wiring, scripts, CI, and documentation, and executed the existing backend and web tests. It does not certify every endpoint or user journey. No existing school database was mutated, no seed or migration was applied, and no paid AI call was made. Findings below are source-confirmed unless an executed check is explicitly named. Installed dependencies were used; a clean installation was not tested. Dependency advisory scanning and live deployment review were outside this pass.

Inventory: 3 applications, 5 shared packages, 85 Prisma models, 58 migration directories, 42 backend controller files, and 52 Next.js page files. Counts describe repository files, not working features or API endpoint counts. The working tree was clean before this audit.

## Prioritized findings

### Critical — public registration can provision administrators

Evidence: `apps/backend/src/auth/auth.controller.ts:10`, `auth.service.ts:26`, and `auth.dto.ts:1`.

`POST /auth/register` has no guard. Its request accepts `roles`, `schoolId`, and `mustChangePassword`. The service normalizes caller-selected role names, creates missing roles, assigns them, and returns a signed token. It only rejects SUPER_ADMIN when schoolId is supplied. Consequently, a caller can request a platform SUPER_ADMIN with no school or a SCHOOL_ADMIN in a chosen school. The permission guard grants these role codes full access. First-login password enforcement does not prevent this: the caller chooses the initial password and can also supply `mustChangePassword: false`.

Required fix: remove public privileged provisioning; bootstrap the first platform admin through an explicit controlled process; require an authorized actor for school account creation; enforce a server-owned role allowlist and transaction. Add HTTP regression tests for both platform and school escalation.

### High — classroom settings return teacher password hashes

Evidence: `apps/backend/src/classroom-management/classroom-management.service.ts`, `settings()`; its controller exposes GET `.../settings` to CLASS_VIEW.

The query includes `teacherAssignments.teacher.user: true` and returns the complete Prisma result. `User.passwordHash` is a normal scalar field. Unlike the teacher/student service response helpers, this path does not remove it; no global response sanitizer was found. A caller with classroom settings access can therefore receive assigned teachers' hashes and unnecessary account fields. These are password hashes, not plaintext passwords, but exposure enables offline cracking attempts.

Required fix: select only required public identity fields in every nested relation. Add an API response test asserting no passwordHash appears at any depth. Review all full User relation responses.

### High — inactive roles still authorize requests

Evidence: `apps/backend/src/auth/permissions.guard.ts:18`, `jwt-auth.guard.ts`, `auth.service.ts` (`me`), and `apps/backend/src/roles/roles.service.ts` (`update`, `remove`).

Roles can be deactivated; deletion of assigned roles explicitly recommends deactivation. However, the central guard loads assigned roles without `role.isActive: true`, then grants their permissions or administrator bypass. JWT role extraction and `/auth/me` likewise do not filter inactive roles. Deactivating a role therefore does not reliably revoke access. Some newer domain services do filter active roles, creating inconsistent behavior across endpoints.

Required fix: centralize active, tenant-valid role resolution and use it for guards, role lists, and permissions. Test an existing token after deactivation.

### High — known fallback signing secret and incomplete session revocation

Evidence: `apps/backend/src/auth/auth.module.ts:16`, `auth.service.ts` (`changePassword`), `jwt-auth.guard.ts`, `apps/web/lib/auth-context.tsx`.

The API silently falls back to a hardcoded JWT signing secret and issues seven-day tokens. A deployment missing JWT_SECRET uses a publicly knowable key. Password changes do not invalidate existing tokens: verification reloads user status but has no token version or password-change cutoff. Browser logout deletes local storage only. Authentication endpoints have no application-level rate limiter in the inspected controller/bootstrap. An external gateway may provide limits, but that is not established here. Browser session tokens are persisted in local storage, increasing the consequence of a script injection.

Required fix: fail startup without a strong configured secret, implement session invalidation and recovery, define a browser session strategy, and enforce login abuse controls. Test revocation explicitly.

### Medium — classroom lesson validation and assignment checks lag newer modules

Evidence: `apps/backend/src/classroom-management/classroom-management.controller.ts` (`createLesson`) and service `createLesson()`.

The legacy lesson endpoint takes `any`, checks a few truthy fields, and validates the section's school scope. It does not verify that subjectId belongs to the selected school/class/year, validate date and coverage ranges, or receive the acting user to check teaching assignment. A user with LESSON_PLAN_MANAGE can create a lesson for a different classroom in the same school if the IDs are known. Arbitrary subject IDs can enter the operation rather than being rejected by a domain check. This differs from homework writes and the newer academic workflow, which enforce actor assignments.

Required fix: adopt strict schemas and explicit actor/scope checks. If broad school-level management is intentional, document that policy and test it consistently.

### Medium — audit logging can silently lose successful mutations

Evidence: `apps/backend/src/audit/audit.interceptor.ts:1`.

Global mutation auditing is fire-and-forget and suppresses database errors. It does not atomically commit with the business mutation and records successful responses only. Several newer services do transactional domain auditing, which is stronger, but coverage is inconsistent.

Required fix: define mandatory audit events and commit them transactionally or through a durable outbox; expose failures operationally. Define separate denied-access/security event logging.

### Medium — broadcast notification read state is shared

Evidence: `apps/backend/src/notifications/notifications.service.ts:1`, schema `Notification`.

Listing and marking notifications read include recipientId null, representing school-wide messages. `markRead` updates a single readAt on that shared notification. One user's read action can consequently mark it read for other users. There is no per-recipient receipt in this flow.

Required fix: use one notification per recipient or a per-user receipt table; test two users reading the same broadcast.

### Medium — classroom report averages mix raw marks

Evidence: `apps/backend/src/classroom-management/classroom-management.service.ts`, `analysis()`.

Classroom analysis averages raw marksObtained across records without normalizing maximum marks or aligning assessment publication/comparability. This can disagree with the newer central analytics, which documents comparable weighted percentages. Attendance also reports zero when there are no records, conflating missing data and actual zero attendance.

Required fix: reuse agreed assessment metrics and explicit no-data semantics; test mixed maximum marks and unpublished assessments.

### Medium — release automation leaves important checks unverified

Evidence: `.github/workflows/ci.yml`, root/app package manifests, `turbo.json`.

CI installs dependencies, generates Prisma, builds, and runs backend tests. It does not invoke the web test suite or provision the opt-in database integrations. It uses npm install rather than npm ci. The root lint command delegates to Turbo, but the inspected web/backend/mobile manifests provide no lint scripts. No complete app deployment, automated backup/restore rehearsal, or migration deployment workflow was found in the inspected tracked infrastructure.

Required fix: add reproducible install, web tests, lint/type checks, disposable-database migration and integration jobs, and a documented release/restore procedure.

### Low — migration readiness does not establish OCR readiness

Evidence: `apps/backend/scripts/check-student-migration.js:5–9`, `migration-extractor.ts:51`.

The script reports localOcr but omits it from ready and the failure exit criteria. It can correctly report ready for structured imports while OCR is unavailable, but an operator may interpret ready as support for all advertised formats. Image/scanned PDF extraction explicitly requires the local English traineddata file.

Required fix: report separate structured-import and OCR readiness, or add a required-OCR mode. A file-presence test alone also does not exercise recognition.

## Corrections to older project documentation

`docs/PROJECT-HANDOFF.md` is dated 5 October and should not be used as the current completion checklist:

- Homework submission updates now check homework, enrollment-school and classroom ownership. The old specific unscoped update finding is fixed in source.
- Classroom loading now filters permitted sources and uses Promise.allSettled. The old all-or-nothing loading finding is fixed in source.
- A parent web page and assessment reports now exist, although the full daily parent portal is unfinished.
- Staff attendance/leave/GPS, unified assessment, CRM/allocation, migration and analytics are materially more developed.
- AI extends beyond standalone lesson generation: the academic workflow generates teaching lessons, papers and insights and saves generation references.
- Backend local environment loading is explicit, CI runs backend tests, and optional Redis caching exists in analytics.
- README, Roadmap and Architecture still describe an early scaffold. Architecture claims a Dockerized app stack, whereas Compose provisions dependencies only.

## Recommended completion order and acceptance gates

1. Close public registration escalation and hash leakage; fix inactive-role resolution and JWT configuration. Gate: unauthenticated callers cannot provision privileges, restricted users cannot elevate or cross tenants, disabled roles stop authorizing, and API JSON never exposes credentials.
2. Run migrations from empty and representative previous schema states on disposable databases; enable the skipped integration suites in CI. Gate: no schema drift, all domain lifecycle/concurrency checks pass, and upgrade/restore instructions are repeatable.
3. Reconcile legacy classroom and newer academic workflow validation, assignment policy and reporting metrics. Gate: an assigned teacher can complete a school day and cannot manage unrelated classrooms.
4. Finish parent onboarding and daily attendance/homework/announcement journeys; implement the selected external delivery channel with durable retries and receipts. Gate: two families and two schools remain isolated and delivery status reflects actual provider outcomes.
5. Establish deployment, persistent private storage, secrets, structured operational logs, readiness checks, backups and restore drills. Gate: a fresh environment can deploy a release and restore school data plus uploaded files.
6. Implement agreed mobile journeys and verify on real devices. Gate: login, teacher work and parent access work against the same secured API.

No completion percentage is assigned: feature counts cannot support an honest percentage without agreed acceptance criteria and live evidence. Existing passing tests are a useful baseline, but the critical security findings take precedence over expanding feature scope.
